# 改动清单（相对 starter kit 基线）

基线：EduSeed C4B `c4b-wechat-publisher-starter.zip` 中的
`scripts/convert_to_wechat.py`、`SKILL.md`、`references/*`。

本技能的全部改动分三类：**修复**（基线有缺陷）、**新增**（基线完全没有），
以及**自身回归修复**（改造过程中我自己引入的缺陷，已修复并加了回归测试）。
每一条都附了可复现的验证方法。

## 一、修复的 5 个缺陷

### 缺陷 1 — 分隔线凭空消失

**现象**：Markdown 里的 `---` 转成 `<hr>` 后，在 `clean_attributes()` 中被当作
非白名单标签 `unwrap()`，结果整条分隔线消失。

**证据**：用基线脚本转换 `examples/demo_all_features.md`（含 1 处 `---`）：

```
hr 分隔线数量: 0
```

**修复**：`sanitize()` 中新增一步，把 `<hr>` 换成带主题分隔符的 `<p>`：

```python
for hr in soup.find_all("hr"):
    p = soup.new_tag("p")
    p["style"] = styles["hr"]
    p.string = divider          # 主题决定，如 "· · ·" / "— — —"
    hr.replace_with(p)
```

**验证**：现在输出中可搜到 `— — —`（blue 主题）。

---

### 缺陷 2 — 引用块丢换行、丢加粗

**现象**：基线用 `p.string = bq.get_text()` 处理 `<blockquote>`，把整块压成
单个文本节点。两个后果：多行内容之间没有任何 `<br>`，公众号里会挤成一行；
内部的 `**加粗**` 也一起丢了。

**证据**：基线输出中的引用块（原文三行，第三行有加粗）：

```
border-left: 4px solid #ddd;">
引用的第一行内容。
引用的第二行内容，验证换行是否保留。
第三行带 加粗强调。
```

—— 换行只是原始 `\n`（HTML 里会渲染成空格），"加粗强调"没有 `<span>` 包裹。

**修复**：改用片段压平函数，把块级段落转成 `<br>` 连接，同时保留行内标签：

```python
def _flatten_to_inline(html_str):
    frag = BeautifulSoup(html_str or "", "html.parser")
    parts = []
    for child in frag.children:
        if isinstance(child, Tag) and child.name in ("p", "li", "h2", "h3"):
            parts.append(child.decode_contents().strip())
        elif isinstance(child, Tag) and child.name == "br":
            parts.append("<br>")
        elif str(child).strip():
            parts.append(str(child).strip())
    return "<br>".join(parts)
```

**验证**：现在引用块里是 `…过程。<br/>如果你也…`，且 `<span style="font-weight: bold;">` 存在。

### 缺陷 3 — 图片没有宽度限制

**现象**：基线只保留 `<img>` 原样，不注入任何样式。公众号正文宽度约 375px，
长图、宽图会直接撑破屏幕。

**证据**：

```
图片标签: ['<img alt="占位图" src="https://example.com/demo.png"/>']
图片含 max-width: False
```

基线自己的 `references/wechat_styles.md` 里明确写了
"Images: always set `max-width: 100%` to prevent overflow"——**文档写了，代码没做**。

**修复**：`sanitize()` 中为所有图片补样式：

```python
for img in soup.find_all("img"):
    img["style"] = styles["img"]   # max-width:100%; height:auto; display:block; margin:18px auto;
    if not img.get("alt"):
        img["alt"] = ""
```

**验证**：`check_wechat_html.py` 中"图片缺 max-width"这条提醒不再触发。

### 缺陷 4 — `ALLOWED_CSS` 是死代码

**现象**：基线第 71 行定义了 CSS 白名单集合，但全文再无引用。
也就是说"过滤非白名单 CSS 属性"这个承诺从未真正执行。

**证据**：

```
$ grep -n "ALLOWED_CSS" convert_to_wechat.py
71:ALLOWED_CSS = {
```

（只有定义，没有使用）

**修复**：新增 `filter_css()`，在输出前对每个 `style` 属性做白名单过滤：

```python
def filter_css(style):
    kept = ["{}: {}".format(k, v) for k, v in _split_style(style)
            if k in ALLOWED_CSS]
    return "; ".join(kept) + (";" if kept else "")
```

**验证**：故意在源文件里写 `<p style="position:fixed;color:red">`，
输出中 `position` 会被丢弃，`color` 保留。

---

### 缺陷 5 — 代码块换行丢失

**现象**：基线把 `<pre><code>` 转成 `<p>` 时用 `p.string = code_text`，
多行代码里的换行符变成裸 `\n`。公众号不认 `<pre>`，也不认裸换行，
结果整段代码被压成一行。同时 `<p>` 里没有等宽字体和换行规则。

**证据**：基线输出：

```
...padding: 16px; margin: 10px 0;">def build_toc(soup, styles):\n    heads = ...
```

**修复**：用 `<br>` 显式表达换行，并补 `white-space: pre-wrap` 与等宽字体：

```python
lines = src.decode_contents().split("\n")
for i, line in enumerate(lines):
    if i:
        p.append(soup.new_tag("br"))
    p.append(NavigableString(html_mod.unescape(line)))
```

**验证**：现在输出中是 `def build_toc(soup, styles):<br/>    heads = ...`，
且样式里含 `font-family: ui-monospace, ...` 与 `white-space: pre-wrap`。

## 一·补、自身引入并修复的 3 个缺陷

> 这三条不是基线的锅，是改造过程中**我自己写出来的**。单独列出来，是因为
> 它们最能说明"为什么必须跑测试和自检"——这类缺陷脚本不报错，只有把输出
> 当成一篇文章读一遍才会发现。

### 缺陷 6 — 目录把 CSS 声明当正文文字输出了

**现象**：文章生成的目录里，每个二级条目前面多出一行明文 `padding-left: 24px;`，
会**直接显示在读者眼前**，非常显眼但也非常容易在长文里被忽略。

**根因**：`build_toc()` 把目录渲染成「单个 `<p>` + `<br>` 串联所有条目」
（公众号里嵌套 `<p>` 不可靠），因此**没有独立的 `<p>` 可以挂 `style`**。
早期实现用了一个 `pad` 变量想表达二级条目的缩进：

```python
num, pad = "—", "padding-left: 24px; "
lines.append('{}<span style="{}">{}</span>&nbsp;&nbsp;{}'.format(
    pad, styles["toc_num"], num, txt))
```

`pad` 被拼进了**文本节点**的位置 —— 它在 HTML 里的落点是文字，不是属性。

**为什么难发现**：脚本不报错、退出码 0、文章正常生成、字数统计也正常，
只是正文里悄悄多了一行垃圾。盯代码看不出来，跑测试当时也测不到（测试
只断言了"目录里有编号"，没断言"可见文字得是干净的中文"）。

**修复**：目录是单 `<p>` 结构，缩进只能用不换行空格实现：

```python
num, indent = "—", "&nbsp;&nbsp;&nbsp;&nbsp;"
```

**验证**：`check_wechat_html.py` 新增第 7 项检查「正文是否泄漏 CSS 声明」。
拿**修复前**的输出跑，当场报错：

```
[错误] 1 项（必须修）
   x 正文里泄漏了 CSS 声明 × 2 —— 样式代码会被当文字显示出来: padding-left: 24px; | padding-left: 24px;
```

拿修复后的输出跑 → `[通过] 未发现问题`。

**回归防护**：新增用例 `修复7 · 目录不得泄漏 CSS 声明（回归）`，断言
"剥掉全部标签和属性后的可见文字里，不得出现 CSS 声明"。这类"断言可见文本
而非原始 HTML"的写法是关键 —— 如果直接对原始 HTML 做正则，样式属性本身
就会命中，测试会永远失败。

### 缺陷 7 — callout 里的列表连同内容被整块丢弃

**现象**：在 callout 里写了一个有序列表（三条问题），生成的 HTML 里
**列表一个字都不剩**，callout 的标题还在。而自检脚本照样报"通过"。

**根因**：callout 最终渲染成**单个 `<p>`**，但 HTML 规则不允许 `<p>` 里
嵌套 `<ol>` / `<ul>`：

```
输入 markdown       →   <ol><li>…</li></ol>
_flatten_to_inline  →   原样返回 <ol>…</ol>（早期只识别顶层 p/li/h2/h3）
_render_callout     →   <p>标题<br><ol>…</ol></p>     ← 非法嵌套
lxml 解析整篇文档    →   <p>标题<br></p><ol>…</ol>      ← 列表被甩出 <p>
替换代码            →   block = fragment.find("p")     ← 只取了那个 <p>
                        holder.replace_with(block)     ← 列表被丢弃
```

**为什么难发现**：不报错、退出码 0，页面上只是"内容少了一段"。
长文里少一段，肉眼很难注意到；而**自检脚本只查标签合规，不查内容完整性**。

**修复**：
1. `_flatten_to_inline()` 重写 —— `ul`/`ol` 压平成 `1. 文字` / `• 文字`
   的行内形式（`<br>` 分隔），并确立一条原则：
   **任何不认识的标签都递归取内容，绝不整块丢弃。**
   顺带补上了 `blockquote`（`> ` 前缀）、`table`（`a | b`）、`hr`（`· · ·`）。
2. 占位符替换改为**取全部顶层块**，不再只取第一个 `<p>`：

```python
blocks = [c.extract() for c in list(root.children) if str(c).strip()]
holder.replace_with(*blocks)
```

**验证**：`修复8` 用例里同时放有序列表和无序列表，断言 5 项文字一条不少，
并断言 callout 内不得残留 `<ol>`/`<ul>` 标签 —— **把根因也变成可检测项，
而不只是检测症状**。

**留下的一条通用结论（已写进复盘 AAR）：**

> 这类问题的共同特征是「**输入里有的内容，没有完整出现在输出里**」。
> 别只针对见过的个案加检查，要写通用断言：
> **输入里的关键字符串，必须都能在输出里找到。**

### 缺陷 8 — callout 标题里的 markdown 格式裸露成星号

**怎么发现的**：定稿后做极端输入自测时，构造了一个
`::: tip 标题带**加粗**` 的用例。输出里标题原样显示成
「💡 标题带\*\*加粗\*\*」—— **两个星号直接印在读者眼前**。
正文里的 `**重点**` 是正常的，只有标题这一行不对。

**根因**：标题和正文走了两条不同的路径。

```python
# 正文：走 markdown 解析 → 星号变成 <strong>
body_md = md_lib.markdown(callout["body"], extensions=[...])

# 标题：只做了 escape → 星号被当作普通文本原样留下
head = '<span style="font-weight:bold;color:{};">{} {}</span>'.format(
    cfg["accent"], cfg["icon"], html_mod.escape(label))
```

`html_mod.escape()` 防的是 HTML 注入（对 `<` `>` `&` 有效），但它**不解
markdown 语法**，所以 `**` 原封不动地留在了文字里。

**为什么难发现**：这是"输出可读但难看"型瑕疵 —— 脚本不报错、自检的 7 项
检查全过、字数统计正常。**只有把它当文章读一遍，并且刚好在标题里写过
markdown 才会看到。** 也正因如此，它在定稿前的 8 轮检查里一直没暴露，
是"极端输入自测"这个动作把它逼出来的。

**修复**：抽出一个 `_inline_md()`，让标题和正文走同一套 markdown 解析。

```python
def _inline_md(text):
    """把一行文本按 markdown 内联语法解析，剥掉外层 <p> 后返回。"""
    frag = BeautifulSoup(md_lib.markdown(text, extensions=["extra"]), "lxml")
    p = frag.find("p")
    return p.decode_contents().strip() if p else html_mod.escape(text)
```

标题里的 `<strong>` 随后会被 sanitize 第 8 步统一转成
`<span style="font-weight: bold;">`，与正文加粗的最终形态一致。

**验证**：新增用例 `修复9 · callout 标题的内联格式不得裸露星号（回归）`。
断言方式是**先剥掉全部标签再看可见文字里有没有裸星号** ——
直接对原始 HTML 做正则会命中 `style` 属性里的内容，测试会永远失败。

**回归安全性**：改完重新生成正式文章，输出文件 md5 与改前**完全一致**
（文章里的 5 个 callout 标题没有使用 markdown 格式），
说明这个修复对既有内容是零影响。

## 一·补二、同步修掉的一个文档缺口

> 这一条不是代码缺陷，是**照着自己写的文档操作会走错路**，同样是自测跑出来的。

**现象**：按 `SKILL.md` 的 Quick Start 执行 `--batch ./drafts` 后，
我去 `drafts/` 找产物，一个 `.html` 都没有 —— 一度判断成"批量模式静默产出零文件"。
实际产物在 `drafts/wechat_output/` 子目录里，**功能完全正常**。

**根因**：文档只写了命令，没写输出落在哪。批量模式的输出目录是
`<输入目录>/wechat_output/`，这个约定仅在代码里体现，从未写进任何文档。

**为什么值得记一笔**：判断错误的人是我，但**错的根源是文档**——
读者按文档操作得到的结果，与文档暗示的预期不一致，就是文档的问题。
"自己照着文档走一遍"之所以必要，是因为**写文档的人会自动脑补没写出来的部分**。

**修复**：Quick Start 里补上每条命令的输出位置。

```bash
# 最简：输出同名 .html（文章.md → 文章.html）
python scripts/convert_to_wechat.py 文章.md

# 批量：转换目录下所有 .md/.docx/.html
# 注意输出不在原目录，而在 <输入目录>/wechat_output/ 子目录里
python scripts/convert_to_wechat.py --batch ./drafts --theme warm
# → ./drafts/wechat_output/a.html、./drafts/wechat_output/b.html
```

## 四、有意保留的基线设计

以下基线设计经评估后保留原样，没有改：

1. **自动安装依赖** —— 保留，但去掉了首次运行时的冗余打印。
2. **`h1` 降级为 `h2`** —— 公众号规则如此，必须保留。
3. **`div` 转 `p`** —— 保留。
4. **`class` / `id` 一律删除** —— 保留，公众号确实不支持。
5. **依赖 `markdown` + `beautifulsoup4` + `python-docx`** —— 保留同一套技术栈，
   不引入新依赖，降低别人的安装成本。
6. **只用 inline CSS，不生成 `<style>` 块** —— 保留，这是公众号的硬性要求。

## 五、测试与自检资产

基线**没有任何测试**。本版把"可验证"做成了技能的一部分：

| 资产 | 内容 |
|------|------|
| `tests/run_tests.py` | **20 个用例**：6 个基线缺陷修复 + 3 个自身缺陷回归 + 11 个新增能力 |
| `scripts/check_wechat_html.py` | 独立的发布前自检，7 项检查（违规标签 / CSS 泄漏 / 图片 / 字数…） |
| `evals/` | **6 个评估用例 × 2 种配置 × 3 轮**，自动判分 + benchmark + 审阅页（见第七节） |
| `新增7 · 极端输入矩阵` | **10 组边界输入**，见下 |

**10 组极端输入矩阵**（这一组是定稿自测时人工构造、事后固化的）：

| 场景 | 期望 |
|------|------|
| 空文件 | 中止并报错（不产出空 HTML） |
| 只有 front matter | 中止并报错 |
| 只有标题 | 正常产出 |
| 无 front matter 的正文 | 正常产出，用默认值 |
| 混入 `<div onclick>` / `<script>` | 清洗标签，**保留文字内容** |
| emoji + 特殊符号 + 中英混排 | 全部保真 |
| callout 内嵌有序列表 | 内容不丢，压平为行内文本 |
| 未闭合的 callout | 内容保留，不崩 |
| 代码块里的 HTML 与 `<` `>` | 正确转义 |
| 超长文章（120 节） | 不截断 |

**为什么把这些写进技能包，而不是只留在交付报告里：**

> 自测如果不固化，就只是一次性验证。**报告记录"我测过"，测试保证"它现在还过"。**
> 下次有人改这个技能时，报告不会替他重跑那 10 组场景，测试会。

**关于断言写法的一条经验**（踩过两次坑）：断言必须**剥掉标签、只看可见文字**。
直接对原始 HTML 做正则会命中 `style` 属性里的内容 ——
例如 `background-color` 里含有 `color:` 这个子串，
会让"5 套主题主色各不相同"的断言永远失败，**看起来像代码坏了，实际上是尺子坏了**。

## 六、第二轮：把"我说它好"换成"量出来它好"

第一轮做完后，对着评分标准自查，发现有三件事我**只有结论，没有证据**：

1. 技能的"图片处理"是 starter kit 里唯一标着 ⚠️ 的短板，而我的演示文章里**一张图都没有**；
2. 我只用 Markdown 试过这个技能，**Word 那条路一次都没走过**；
3. 我一直在说"比原版好"，但**从来没有量过好多少**。

三条是同一个毛病。于是补了下面三块。

### 6.1 本地图片处理（`resolve_images()`）

公众号的图片有三种典型死法，而且**在页面上看起来都是"一张没出来的图"**：

| 情况 | 原因 | 处理 |
|------|------|------|
| 外链图片 | 需要先上传到素材库 | 保留原样 + 显式告警 |
| 本地路径 | 编辑器读不到你硬盘上的文件 | 读成 base64 data URI 嵌进 HTML |
| SVG | 公众号保存后会丢掉 | **不嵌入**，告警让用户先转 PNG |
| 文件不存在 | 路径写错/图被移走 | 保留原路径 + 显式告警（绝不静默） |

另外两件事：统一注入 `max-width`（默认 100%，`--image-width` 可调），
以及把 markdown 的 alt 文本渲染成居中小字图注。

**设计上最刻意的两点**：

- **四类风险必须分别报出来**。只报"图片处理完成"等于把失败藏起来 ——
  这四种的用户动作完全不同（上传 / 补路径 / 转格式 / 修路径）。
- **图片告警不受 `--quiet` 抑制**。`--quiet` 是给批量场景降噪用的，
  但"图片丢了"不属于噪音。

开关：`--no-embed-images`（只留原路径）、`--no-captions`（关图注）、
`--image-width 80%`。自检脚本同步新增了"图片没嵌入"这一项。

### 6.2 一稿多投与体裁模板（`scripts/export_formats.py`）

同一份源稿，三个出口：

| 出口 | 处理方式 |
|------|---------|
| 公众号 HTML | 交给主转换脚本，走完整清洗与排版 |
| 知乎 Markdown | 保留 markdown 结构；callout 降级成 `>` 引用块（知乎原生支持） |
| 纯文本 | 剥掉全部标记，callout 变 `【标题】`，适合发群/邮件/工单 |

设计原则写进了脚本头部：**源稿是唯一真相，格式只是出口** ——
不要为了适配某个平台去改源稿，否则三份内容会开始漂移。

顺带做了 4 套体裁骨架（`templates/`）：技术教程 / 学习心得 / 技能介绍 / 复盘总结。
用 `--new <模板> <路径>` 起稿，目标文件已存在时**拒绝覆盖**（起稿是常见动作，
静默覆盖别人的稿子是事故）。

### 6.3 真的量一次：skill-creator 的 eval 流程

这是第二轮里最重的一块，也是最应该早点做的一块。

**做法**：`evals/evals.json` 定义 6 个用例（prompt + 预期 + 输入样例），
`evals/run_evals.py` 负责执行与判分：

```
6 个用例 × 2 种配置（with_skill / without_skill）× 3 轮 = 36 次运行
```

- `with_skill` = 本技能包
- `without_skill` = **starter kit 的原版脚本**（就是那个 `c4b_starter` 目录里的）

**为什么要跟原版比，而不是跟"什么都不做"比**：因为挑战的起点就是 starter kit，
拿它当基线才能回答"我的改造到底加了什么值"。

**结果**：

| 用例 | with_skill | without_skill | 差值 |
|------|-----------|---------------|------|
| 基础转换 | 100% | 100% | +0% |
| 主题 + 目录 + 元数据 | 100% | 50% | +50% |
| 高亮框 | 100% | 75% | +25% |
| 结构元素（分隔线/引用/代码块/表格） | 100% | 20% | **+80%** |
| Word 输入 | 100% | 40% | +60% |
| 中英混排 + 图片 | 100% | 50% | +50% |
| **总体** | **100%** | **55.8%** | **+44 个百分点** |

**最值得记的一条**：在"基础转换"上两个版本**打平**。原版把最基础的事做得没问题 ——
它是别人认真写过的东西。差别全出在它没有的地方。这条结论比"我全面胜出"可信得多。

**两个工具是 skill-creator 自带的**，不是我重写的：`scripts/aggregate_benchmark.py`
生成 `benchmark.json` / `benchmark.md`，`eval-viewer/generate_review.py --static`
生成可离线打开的审阅页。判分逻辑是自己写的脚本（见下面 6.4 的教训），
因为**判分必须可复现** —— 同一份输出今天判过、明天判不过，benchmark 就没有意义。

### 6.4 一条被我改掉的判据（失败经验）

第一次跑 eval，有一格结果很刺眼：**Word 用例上，我的版本反而输给了原版（2/4 vs 3/4）**。

我原本写的判据是"输出里至少要有 5 个段落"。查完发现：

- 我的版本把 Word 的列表**正确地**渲染成了 `<ul>/<ol>+<li>`；
- 原版不认列表样式，把 4 个列表项**全压成了普通 `<p>`** —— 段落数自然更多。

**数段落个数，会把"丢结构"判成"更完整"。** 输的不是代码，是尺子。

改法：把"≥5 个 `<p>`"换成内容保真断言 ——
**"Word 里的每一段文字（标题/正文/列表项/引用/表格单元格）都必须出现在输出里"**，
再加"列表必须保留为 `ul/ol`"和"表格必须保留为 `table`"。
改完 with_skill 满分，原版掉到 40%。

> **这是同一种错误在本次改造里第三次出现**（前两次：数 `<p>` 之前先用错搜索串判定"分隔线不见了"、
> 用 `background-color` 的 `color:` 子串误判主题色相同）。
> 三次都是**断言错了，代码是对的**。
> 已经写成规矩：**看到红灯，先怀疑断言，再怀疑代码。**

### 6.5 分析师一遍

`run_evals.py` 的 `analyze()` 对应 skill-creator 的 analyzer 步骤，输出三条结论：

1. **14 条断言在两种配置下都通过**（basic×4、themed×2、callouts×3、structure×1、
   sample-report×2、cjk-images×2）—— 它们测的是基线也具备的基本功，
   **对本次对比不产生信息量**，下次迭代应换成更难的判据。
2. **每个「用例 × 配置」的 3 次运行结果完全一致，方差为 0**。
   这是确定性脚本该有的样子，可复现性好；但换个说法，**这也是一种"假稳定"**
   —— 换成真人来用，输入千变万化，它未必还这么稳。
3. **区分度最高的用例是结构元素（+80%），最低的是基础转换（+0%）**。

这三条都是**对自己不利**的结论，但它们是这次评估里最有价值的部分。

## 七、第三轮：把 Level 4 缺的两项补上

对着挑战原文逐条核之后发现，Level 4 的五项里有**一项完全没做、一项只做了一半**：

| 挑战要求 | 当时的状态 |
|---------|-----------|
| 写作辅助集成：**从大纲生成初稿** | ❌ 没有。我有 4 套体裁模板，但那是"给骨架填空"，不是"从大纲生成" |
| SEO/阅读体验优化：**自动**加标题摘要 | ⚠️ 摘要靠 front matter 手填，是半自动 |

这两项都能自己补，就补了。

### 7.1 从大纲生成初稿（`scripts/outline_to_draft.py`）

输入一份提纲（章节 + 要点），输出一份能直接往下写的初稿：

```bash
python scripts/outline_to_draft.py 大纲.md 初稿.md --author "李瑞翔"
```

做的事情：解析大纲层级 → 生成 front matter → 把要点按章节摆到位置上 → 插入写作提示（HTML 注释）→
补一个结语章（大纲里已经写了就不重复加）。

**和 `templates/` 的区别**（这两个东西最容易混，所以在脚本注释和 SKILL.md 里都写了一遍）：
`templates/` 是**空骨架**——章节标题是固定的，你往里填；本脚本是**按用户的大纲生成**——
章节来自用户的提纲，要点已经被摆到该在的位置上。挑战要的是后者。

解析用的是**逐行状态机，不是正则切块**。理由和 `export_formats.py` 里 `split_blocks()` 那次一样：
正则处理嵌套结构一旦切错是静默出错（少一段或多一段，没人会注意），逐行读代码长一点，但每行的归属都是显式判断的。

两个开关：
- `--sections`：把每个要点提升为 `### 小节标题`（默认只保留为要点清单）
- `--no-tips`：不插写作提示

**不覆盖已有文件**（要 `--force`）——手滑毁掉正在写的稿子，比少个功能麻烦得多。

### 7.2 自动标题摘要（`derive_meta()` + `_pick_summary()`）

转换时如果 front matter 没写标题/摘要，就从正文里提取：

- 标题：取 `h1`，**并从正文移除**（已经在头部当大标题了，正文再来一次就是重复）
- 摘要：取第一个合适的段落

优先级始终是 **命令行 > 文件头 > 自动提取**，自动值只在缺失时兜底，不覆盖用户写的任何东西。
`--no-auto-meta` 可关闭。

**这里踩了一个坑，是测试帮我抓到的 —— 见 7.4。**

### 7.3 HTML 注释一律剥离

`outline_to_draft.py` 生成的写作提示是 HTML 注释。写的时候看得见，但**成品里不该出现**。
公众号编辑器对注释的处理不明确，留着只是增加不确定性。所以在 `sanitize()` 里加了第 1 步：删掉所有注释节点。

### 7.4 失败经验：摘要把一行 CSS 当成了摘要

改完自动摘要，跑测试，`修复7 · 目录不得泄漏 CSS 声明` 挂了：

```
[FAIL] 修复7 -> 行内代码里的 CSS 示例被误判为泄漏
```

这条用例里有一段**反向检查**：喂一句含行内代码的正文
（`正文里引用了 \`padding-left: 24px;\` 这样一个例子。`），
确认自检脚本**不会**把它误判成"正文泄漏 CSS"。

我改了自动摘要之后，这句 30 多字的正文**正好满足"第一个≥20 字的段落"**，
于是被提取成了摘要 → 摘要出现在头部 → 自检在可见文字里发现 `padding-left: 24px;` → 报泄漏。

**测试没有误报，是我新加的功能把好文章搞坏了。** 而且这个坑很隐蔽：
真实的文章里，如果第一段恰好是一句带代码的话，摘要就会变成一行样式代码。

改法：摘要候选段落要过两道筛——
- 含 `<code>` 的段落**跳过**（读者点开摘要看到的会是一段代码）
- 匹配样式声明模式的**跳过**（用的正则和自检脚本判断"泄漏"的**同一套**，保持一致）

同一轮里还有一处正常的行为冲突：`修复1` 原来用 `# 一级标题` 开头的输入，
现在这个 `h1` 被自动标题拿去并移出正文了，于是"h1 降级为 h2"这条测不到。
处理方式是**给该用例的输入加一段 front matter**（真实文章都写 front matter），
而不是把自动标题关掉——因为无 front matter 时的行为由新增的 `新增11` 单独覆盖。

> 这一轮再次印证：**改了一个地方，被影响的地方往往不在你改的那个文件里。**
> 20 个用例跑下来，我自己没发现的问题，测试发现了 2 个。

| `新增11 · 自动标题摘要与注释剥离` | 自动补标题（正文那份被移除）、自动补摘要、已有值不被覆盖、含代码段落不当摘要、注释剥离、`--no-auto-meta` 生效 |

## 八、第四轮：干净目录复跑暴露的一次回退

这一轮**没有新增能力**，只有一处行为修正。起因是收尾时把最终打包物解压到空目录、
当成"别人的机器"重跑一遍 eval —— 结果 `with_skill` 只有 93.3%（`eval-3-structure` 60%），
和文档里写的 100% 对不上。

### 8.1 根因：自动摘要把正文首段"复读"了一遍

第三轮新增的自动摘要（见 7.2）会从正文里挑一段当摘要，然后 `build_header()`
**又把它渲染到头部** —— 同一句话在文章里出现两次。

连带后果：摘要块的样式与引用块相同（都带 `border-left: 4px solid`），摘要又排在正文最前，
于是 `evals/run_evals.py` 里的 `block_of(html, "border-left")` 抓到的是**摘要块**，
"引用块多行换行""引用块加粗保留"两条断言全判否。

### 8.2 修法：改产品行为，不改判据

自动提取的摘要**只当元数据**，不再往头部渲染；`build_header()` 只渲染"用户自己写了 `summary:`"的那份。

```python
# derive_meta()
if meta["summary"]:
    meta["_summary_auto"] = True

# build_header()
if meta.get("summary") and not meta.get("_summary_auto"):
    ... 渲染摘要块 ...
```

理由：**判据没写错 —— 是同一句话真的出现了两次。**
自动摘要来自正文，它本来就在文章里；再渲染一遍不是"加了摘要"，是"复读"。
用户显式写 `summary:` 的场景不受影响，照常渲染。

### 8.3 测试资产

`tests/run_tests.py`：用例数不变（**20**），但 `新增11` 的断言收紧了：

| 断言 | 原来 | 现在 |
|------|------|------|
| 自动摘要段落在成品里的出现次数 | 2 次（头部 + 正文） | **1 次**（不应复读） |
| 含代码段落不得当摘要 | 1 次 | 1 次（不变） |
| 自动补全提示 | — | 输出里必须出现"已自动补全"（否则摘要补了等于没补） |

### 8.4 复验

- 重新打包：`quick_validate.py` → `Skill is valid!`；`package_skill.py` → zip **138,409 字节**
- 解压到一个**全新的空目录** → `tests/run_tests.py` **20/20 通过**
- 同目录重跑 eval → **with_skill 100.0% / without_skill 55.8% / delta +0.44**（六条用例全 100%，3 次运行方差为 0）
- `eval-3-structure` **5/5**：引用块内换行 2 个、加粗保留

### 8.5 失败经验

**文档里的测试数字，必须是"最后一次改动之后"跑出来的。**
第三轮改完代码后我沿用了上一轮的 eval 数据 —— 六条用例里只有一条受影响，
偏偏这种"看起来没问题"的结果最容易被直接抄进报告。

**"把包解压到空目录重跑一遍"不是走形式**，它是唯一能发现"我手里的还是旧数据"的办法。
